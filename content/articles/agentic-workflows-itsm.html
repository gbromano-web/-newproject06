IT service desks have automated simple tasks for years with scripts and workflow rules. What's new is software that can interpret an unstructured request, gather context from several systems, decide what to do and then do it. These AI agents can take on much more of the work, which makes it more important to decide carefully which work they should take.

This guide offers a simple autonomy scale, maps common service management tasks onto it, and sets out the controls that make agent actions safe and auditable.

An autonomy scale for service management

Rather than deciding whether to "use agents", decide how much autonomy each task gets. Four levels cover most cases:

Autonomy levels for AI agents in IT service management
LevelWhat the agent doesWho is accountable
1. SuggestRecommends a category, a knowledge article or a next step; a person decidesThe person
2. DraftPrepares the action, such as a reply or a change request, for a person to approve and sendThe approver
3. Act within limitsCarries out pre-approved, reversible actions on its own and records themThe owner of the pre-approved procedure
4. Act and reportActs more broadly and informs people afterwardsRarely appropriate in IT operations today

This scale is our own framing rather than an industry standard, but it maps neatly onto how service management already handles risk: some changes are pre-approved, most need approval, and some are emergencies.

Mapping common tasks

Ticket triage and routing: level 3 is reasonable

Classifying tickets, setting priority from the description, spotting duplicates and routing to the right queue are high-volume, low-risk and easy to correct. A misrouted ticket costs minutes, not an outage. These are good first candidates for autonomous action, with agents' decisions sampled and reviewed each week.

Answering questions: level 2 or 3, depending on the topic

Answering "how do I connect to the VPN?" from the knowledge base can be autonomous if answers cite their sources and the user can escalate easily. Answers about HR, security or anything with legal weight are better drafted for an agent to send. Evaluate answer quality the same way you would any retrieval-based assistant.

Password and MFA resets: keep identity verification strong

Resets look like ideal automation candidates, and the mechanics are. But they are also a favourite route for social engineering: an attacker who convinces the service desk to reset someone's MFA has bypassed it. An agent doesn't remove that risk; it can scale it. Automate the reset itself only after strong, phishing-resistant identity verification, and route anything unusual — a privileged account, a new device, an unfamiliar location — to a person.

Runbook execution: level 3 only for standard changes

Restarting a stuck service, clearing a full disk, scaling a pool within set bounds: these are the kinds of action agents can execute well, if they are written down, reversible and pre-approved. Anything outside the runbook goes back to a person.

Change approval: humans stay accountable

Agents can do useful work on change requests: drafting them, checking them against policy, summarising the risk and the rollback plan, and flagging conflicts with other scheduled changes. The decision to approve a normal change should stay with a person or a change board, because someone has to be accountable for it.

Incident communication: level 2

Drafting status updates from incident timelines saves time during an outage. Have a person approve them before they reach customers or executives; a confident, wrong update during an incident does real damage.

Use the change types you already have

ITIL-based change practice already distinguishes how much scrutiny a change needs. In ServiceNow's documentation, for example, a standard change is a pre-authorised change that is low risk and relatively common; an emergency change must be implemented as soon as possible, for example to resolve a major incident; and a normal change is any change that is neither.

This gives you a ready-made boundary for agents:

  • Standard changes can be executed autonomously, because they were assessed and approved once, as a procedure. Each new procedure an agent may run should go through the same approval as any other standard change.
  • Normal changes can be drafted and assessed by an agent, but approved by people.
  • Emergency changes need human judgement under pressure. Agents can gather data and propose actions; a person decides.

Using existing categories also helps with auditors: you can explain agent behaviour in terms the change process already defines.

Controls every agent needs

  • Least-privilege credentials. Each agent gets its own identity with only the permissions its approved tasks need. Never reuse a human administrator's account or a broad service account.
  • An allow-list of actions. Agents should call specific, approved tools, such as "restart service X", rather than having general shell or API access. The OWASP Top 10 for LLM applications calls the opposite "excessive agency".
  • Treat ticket content as untrusted input. A ticket can contain text written to manipulate the agent, a form of prompt injection. An agent reading a ticket must not be able to escalate its own permissions because of what the ticket says.
  • Full audit logging. Record what the agent saw, what it decided, which tool it called with which parameters, and the result. Link each action to the ticket.
  • Limits and an off switch. Rate-limit actions, cap how many systems an agent can touch in a period, and make sure someone on call can disable it immediately.
  • Rollback for every action an agent can take autonomously. If an action can't be undone, it isn't a level 3 task.

Rolling it out

  1. Start at level 1 for a chosen queue, and compare the agent's suggestions with what people actually did.
  2. Move individual tasks up a level only when their suggestions have been consistently right, and the cost of a mistake is low.
  3. Review a sample of agent actions every week, including ones nobody complained about.
  4. Treat agent mistakes as incidents: record them, find the cause, and add a test or a control.
  5. Document the arrangement in your risk register: which tasks run at which level, who owns them, and when they are reviewed. NIST's AI Risk Management Framework is a helpful structure for this.

The organisations that get the most from agents tend to be those that expand autonomy deliberately, one task at a time, with evidence for each step. That is also what makes the arrangement defensible when an auditor, or an incident review, asks why the agent was allowed to do what it did.
