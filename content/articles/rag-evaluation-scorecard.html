Retrieval-augmented generation, or RAG, is the most common way to build an internal assistant: when someone asks a question, the system searches your documents, passes the most relevant passages to a language model, and asks it to answer using them. Done well, it gives employees answers grounded in your own policies, runbooks and product documentation.

Done badly, it produces fluent answers that cite the wrong version of a policy, or reveal a document the person asking should never have seen. This guide sets out how to evaluate a RAG assistant before launch and after every change, using a scorecard you can track over time.

Evaluate the two halves separately

A RAG system has two stages that fail in different ways:

  • Retrieval finds the passages to give the model. If it returns the wrong documents, or misses the right one, no model can produce a correct grounded answer.
  • Generation writes the answer from those passages. Even with perfect context, the model can ignore it, overstate it, or fill gaps with plausible inventions.

Measuring only the final answer hides which stage failed. When you score retrieval and generation separately, a drop in quality points straight to where to look: the index, the chunking and the search settings, or the prompt and the model.

Build a test set from real questions

Evaluation is only as good as the questions you test with. Build a set of a few hundred questions, and keep growing it:

  • Source questions from reality: help desk tickets, internal chat channels, search logs from your intranet. Real questions are messier and more useful than invented ones.
  • For each question, record the expected answer and the source document (or documents) that contain it. The source is what lets you measure retrieval.
  • Include questions that should not be answered: questions with no answer in your documents, and questions about restricted documents asked by users without access. The right behaviour is to say so.
  • Cover each content area roughly in proportion to how often people ask about it, plus extra cases for high-risk areas such as HR, security and finance policies.

Subject-matter owners should check the expected answers. A test set with wrong answers will reward a system for being wrong.

Measuring retrieval

With known source documents for each question, retrieval quality is measurable without any model judgement:

  • Hit rate at k: how often at least one correct source appears in the top k retrieved passages. If the right document isn't there, the answer can't be grounded.
  • Context precision: how much of what was retrieved is relevant, and whether relevant passages are ranked above irrelevant ones. Low precision means the model has to work through noise.
  • Context recall: how much of the information needed for the expected answer is present in the retrieved context.

Context precision and recall are among the metrics popularised by the open-source Ragas framework, which estimates them using a language model as a judge when you don't have passage-level labels.

When retrieval scores are poor, look first at chunking (passages split mid-thought, or too large to rank well), at whether search combines keyword and semantic matching, and at whether stale duplicates of a document compete with the current version.

Measuring generation

Faithfulness

Faithfulness measures whether an answer sticks to its sources. Ragas defines it as the number of claims in the response supported by the retrieved context, divided by the total number of claims in the response, giving a score from 0 to 1. A low score means the model is adding information the documents don't contain, which is exactly the failure that erodes trust.

Answer relevance and correctness

Relevance asks whether the answer addresses the question. Correctness compares it with the expected answer in your test set. An answer can be perfectly faithful to the retrieved context and still wrong, because retrieval returned an outdated document; that is why correctness and retrieval metrics have to be read together.

Using a model as a judge

Most generation metrics use a language model to judge another model's output. That scales, but judges make mistakes and have biases of their own. Calibrate them: have people score a sample of a hundred or so answers, compare with the automated scores, and keep spot-checking a sample at every release.

Permissions: the test that can't fail

An internal assistant usually indexes documents with very different audiences: company-wide policies, team wikis, HR records, board papers. If retrieval ignores document permissions, the assistant becomes a way around them.

  • Enforce permissions at retrieval time, filtering results by the identity of the person asking, using the same access rules as the source system.
  • Keep permissions in sync. When access to a document changes in the source, the index must reflect it quickly.
  • Test it directly: for every restricted document in your test set, ask about it as a user without access and confirm it is never retrieved or quoted.

Treat any failure here as a release blocker, not a score to improve. The OWASP Top 10 for LLM applications lists sensitive information disclosure among the main risks for these systems.

Freshness

Internal documents change constantly. An assistant that answers from last quarter's travel policy is worse than no assistant, because it sounds authoritative.

  • Measure indexing lag: the time between a document changing in the source and the change being searchable.
  • Remove superseded versions from the index, or rank them clearly below the current version.
  • Add "changed recently" questions to your test set whenever an important policy is updated, with the new answer as the expected one.
  • Show sources and their dates in every answer, so employees can check what the assistant relied on.

After launch

Offline tests catch regressions; production feedback finds the gaps your test set missed. Collect thumbs-up and thumbs-down ratings with an optional comment, review the negative ones weekly, and turn the instructive ones into new test cases. Over time, the test set becomes a record of everything the assistant has got wrong, which is exactly what you want to keep testing against.

For governance, map the scorecard to your organisation's risk process. NIST's AI Risk Management Framework is a useful structure for documenting what you measure, who owns each risk and how often it is reviewed.
