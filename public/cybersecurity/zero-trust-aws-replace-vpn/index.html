    Zero Trust on AWS: replacing your VPN with identity-aware access

    A phased migration plan using AWS Verified Access, the identity provider you already run, and device posture signals, so you can retire network-level trust one application at a time instead of in a single risky cutover.

    For most enterprises, the corporate VPN started as a convenience and became a liability. It grants a device a network address inside your perimeter, and from that point on, reachability is the default. Every internal app behind it inherits the same coarse trust decision that was made once, at connection time.

    Identity-aware access flips that model. Instead of asking “is this device on our network?”, every request asks “is this user, on this device, in this state, allowed to reach this specific application right now?” On AWS, the managed building block for that is AWS Verified Access. This guide walks through how to adopt it incrementally, what the policies look like, and where teams usually get stuck.

    Why VPNs became the bottleneck

    The problems with VPN-centric access are rarely about the tunnel itself. They come from what the tunnel implies:

    • Lateral movement. A compromised laptop on the VPN can usually reach far more than the one app its user needed.
    • Coarse authorization. Access is decided by network segment and security groups, not by who the user is or what their device looks like at that moment.
    • Operational drag. Concentrators need capacity planning, split-tunnel debates never end, and contractors get full network access because scoping it is tedious.
    • Weak audit trail. Logs show that a device connected, not which application requests a specific identity made.

    None of this means you rip the VPN out on day one. It means you stop adding new applications behind it, and you start moving existing ones to a model where every request is evaluated.

    How identity-aware access works on AWS

    Verified Access sits in front of your internal applications — whether they run behind an Application Load Balancer, a Network Load Balancer, or a network interface — and evaluates each HTTP(S) request against a policy before forwarding it. The pieces you configure are:

    • Trust providers supply the signals. A user identity trust provider is either IAM Identity Center or any OIDC-compatible IdP (Okta, Microsoft Entra ID, Ping and others). A device trust provider brings posture data from supported endpoint vendors.
    • A Verified Access instance ties trust providers together and is where logging is configured.
    • Groups collect applications with similar security requirements and share a group-level policy.
    • Endpoints represent individual applications, each with an optional endpoint-level policy that further narrows access.

    Policies are written in Cedar, AWS's open-source policy language. Because policies are evaluated on every request, a user whose device falls out of compliance — disk encryption disabled, EDR agent stopped — loses access on their next request rather than at the next VPN reconnect.

    A reference architecture that scales

    Teams that succeed with this pattern tend to make the same structural decisions early:

    1. Group by sensitivity, not by team. Create a small number of Verified Access groups — for example general-internal, finance-restricted, and production-admin — and put the strict rules at the group level so new apps inherit them automatically.
    2. Keep applications private. Load balancers behind Verified Access should be internal. The only internet-facing component is the Verified Access endpoint itself.
    3. Use IdP groups as the source of truth. Avoid hard-coding email addresses in policy. Map access to directory groups that are already governed by joiner-mover-leaver processes.
    4. Send logs somewhere you query. Verified Access can log to CloudWatch Logs, S3, or Kinesis Data Firehose. Route them into your SIEM on day one; per-request logs are one of the biggest security wins of the migration.
    5. Manage everything as code. Instances, groups, endpoints and policies are all supported by CloudFormation and Terraform. Policy changes should go through review like any other access change.

    Writing your first Cedar policies

    Start with a group policy that requires an authenticated user from a known directory group and a device reported as low risk. The exact attribute paths depend on the policy reference name you give each trust provider — here they are named idp and device.

    // Group policy: general-internal
permit(principal, action, resource)
when {
  context.idp.groups.contains("eng-all") &&
  context.device.risk == "LOW"
};

    Then tighten individual endpoints. A finance application might additionally require that the user belongs to a specific group and that their email is verified by the IdP:

    // Endpoint policy: finance-reporting
permit(principal, action, resource)
when {
  context.idp.groups.contains("finance-analysts") &&
  context.idp.email_verified == true &&
  context.device.risk == "LOW"
};
    Check the claim shape before you write policy. Every IdP and device provider structures claims slightly differently. Turn on Verified Access logging with trust context included, make a test request, and read the actual claims from the log before writing conditions against them. Most “policy denies everything” tickets come from a mismatched attribute name.

    A phased migration plan

    The safest migrations run the VPN and identity-aware access side by side and move applications in waves, starting with the ones that have the lowest blast radius and the most enthusiastic users.

    Phased migration from VPN to identity-aware access
    PhaseScopeExit criteria
    0 · Foundations (2–3 weeks)Trust providers, one instance, logging to SIEM, IaC pipelineTest app reachable with policy enforced; logs visible in SIEM
    1 · Pilot (3–4 weeks)2–3 low-risk web apps (wiki, internal dashboards), IT and security staff onlyNo access regressions for two weeks; help desk runbook written
    2 · Expand (6–10 weeks)All browser-based internal apps, all employeesMajority of web traffic off the VPN; posture enforcement on
    3 · Restricted appsFinance, HR, admin consoles with endpoint-level policiesAccess reviews signed off by data owners
    4 · Shrink the VPNRemaining non-HTTP protocols; contractors moved off VPNVPN limited to named exceptions with an end date

    Common pitfalls (and how to avoid them)

    Treating non-HTTP traffic as an afterthought

    Database clients, SSH and RDP don't behave like browser apps. Verify which protocols and endpoint types your Verified Access configuration supports in your target regions, and plan a separate path — for example Session Manager for shell access — for anything that doesn't fit. Do this in phase 0, not phase 4.

    Posture checks that lock out the CEO on a Monday

    Roll out device policies in log-only mode first: write the policy permissively, log the device claims, and measure how many real requests would have been denied. Only enforce once the non-compliant population is small and has a remediation path.

    Forgetting break-glass access

    If your IdP has an outage, identity-aware access fails closed — which is correct, but it needs a documented, tested emergency path for production administrators that is monitored and reviewed after every use.

    Skipping the cost model

    Verified Access is billed per application-hour plus data processed. For a handful of high-value apps the cost is easy to justify; for hundreds of low-traffic internal tools, compare it against consolidating apps behind fewer endpoints, and against the fully loaded cost of running and patching VPN infrastructure. Check the current AWS pricing page for your regions rather than relying on old estimates.

    Key takeaways

    • Stop adding new apps to the VPN; route them through identity-aware access from day one.
    • Put strict rules in group policies so every new endpoint inherits them.
    • Read real claims from logs before writing Cedar conditions.
    • Enforce device posture only after a log-only measurement period.
    • Design break-glass access and non-HTTP paths before the pilot, not after.
