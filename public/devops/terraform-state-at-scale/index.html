    Terraform state at scale: remote backends, locking, and drift detection

    One state file works until it doesn't: plans slow down, locks collide, and a single mistake can touch everything. Here is how to split state by blast radius, lock it safely, and catch drift before an incident does.

    Terraform state is the record of which real resources Terraform manages and how they map to your configuration. Early on, one state file per environment is fine. As an estate grows, the same layout starts to hurt: plans take minutes, two teams collide on the same lock, and every apply carries the risk of touching resources nobody meant to change.

    This guide covers how to split state, how to configure a remote backend with locking, how to migrate off the older DynamoDB locking, and how to detect drift. Examples use the S3 backend because it is the most common; the principles apply to other backends.

    Split state by blast radius

    The question to ask of any state boundary is: if an apply in this state goes wrong, what is the worst it can break? A single state holding the network, the databases and every application can break all of them at once. Smaller states limit the damage, speed up plans and reduce lock contention.

    Good boundaries usually follow three things:

    • Lifecycle. Things that change rarely, such as network foundations and DNS zones, should not share state with things that change daily, such as application services.
    • Ownership. Each state should have one owning team. Shared ownership is how locks collide and reviews get skipped.
    • Environment and region. Production and non-production never share state, and multi-region estates usually separate state per region.

    Don't go too far the other way. Hundreds of tiny states each holding two resources create their own overhead: dependency ordering across states becomes a manual process. Aim for states that one team can plan in under a minute or two and reason about in one review.

    Configure the remote backend

    Remote state belongs in a dedicated, tightly controlled bucket, never in version control: state can contain secrets such as database passwords and generated keys, in plain text.

    terraform {
  backend "s3" {
    bucket       = "acme-tfstate-prod"
    key          = "prod/eu-west-1/network/terraform.tfstate"
    region       = "eu-west-1"
    encrypt      = true
    kms_key_id   = "arn:aws:kms:eu-west-1:111122223333:key/EXAMPLE-KEY-ID"
    use_lockfile = true
  }
}

    What each security-relevant setting does:

    • encrypt enables server-side encryption of the state file and lock file; kms_key_id uses your own KMS key, so access to state also requires permission on that key.
    • use_lockfile turns on S3 native state locking, described below.
    • The key path mirrors the directory layout, so it is obvious which configuration owns which state.

    Two settings live on the bucket rather than in Terraform. HashiCorp highly recommends enabling bucket versioning, so a corrupted or accidentally deleted state can be recovered. And the bucket policy should limit read access to the pipelines and people who need it, because anyone who can read state can read whatever secrets it contains.

    State locking with use_lockfile

    Locking stops two runs from writing the same state at once, which would corrupt it. Historically the S3 backend needed a DynamoDB table for this. Terraform 1.10 introduced native S3 locking as an opt-in feature: with use_lockfile = true, Terraform creates a lock file next to the state file, with the same name and a .tflock extension.

    The S3 backend documentation now states that DynamoDB-based locking is deprecated and will be removed in a future minor version. New backends should use use_lockfile.

    The lock file needs IAM permissions of its own. The principal running Terraform needs s3:GetObject, s3:PutObject and s3:DeleteObject on the .tflock object, in addition to its permissions on the state file. A bucket policy that only allows access to *.tfstate objects will make every run fail to acquire a lock.

    Migrating off DynamoDB locking

    You can migrate without downtime, because the backend supports both mechanisms at once. When both are configured, Terraform acquires a lock from both before proceeding, so runs on old and new configurations still exclude each other.

    1. Grant the lock file permissions above to every pipeline and role that runs Terraform.
    2. Add use_lockfile = true alongside the existing dynamodb_table setting, and run terraform init -reconfigure.
    3. Once every pipeline and engineer is on the new configuration, remove dynamodb_table and re-initialise.
    4. Keep the DynamoDB table until you've confirmed nothing still references it, then delete it.

    Sharing values between states

    Split state creates a new question: how does the payments service find the network's subnet IDs? There are three common patterns:

    Ways to share values between Terraform states
    PatternHow it worksTrade-off
    Remote state data sourceThe consumer reads the producer's outputs with terraform_remote_stateSimple, but the consumer needs read access to the producer's whole state, secrets included
    Parameter storeThe producer writes chosen values to a store such as SSM Parameter Store; consumers read only thoseLeast privilege and explicit contracts; one extra resource to manage
    Provider lookupsThe consumer finds resources by tag or name with data sourcesNo coupling to the producer's state, but lookups can silently match the wrong resource

    For larger estates, the parameter store pattern tends to hold up best, because it treats each published value as an interface and avoids granting broad read access to state.

    Detect drift before it detects you

    Drift is any difference between the real infrastructure and what the state and configuration expect: a security group rule added in the console during an incident, a tag changed by a script, a resource deleted by hand. Drift is dangerous because the next apply may undo an emergency fix, or fail halfway through.

    The simplest reliable detector is a scheduled plan in CI. The -detailed-exitcode flag makes terraform plan return exit code 0 when there are no changes, 1 on error, and 2 when changes are present. Capture the code explicitly, because most CI shells stop at the first non-zero exit:

    terraform init -input=false
status=0
terraform plan -input=false -lock=false -detailed-exitcode -out=drift.tfplan || status=$?
if [ "$status" -eq 2 ]; then
  echo "Drift detected"   # post the plan summary to the owning team's channel
fi
exit $(( status == 1 ))   # fail the job only on real errors

    Run it against every state on a schedule, nightly for production. Using -lock=false keeps the read-only check from blocking real deployments; it never applies anything. For changes made outside Terraform that you want to accept rather than revert, terraform plan -refresh-only shows how the state would be updated to match reality.

    Route each drift report to the team that owns that state. A drift report that goes to a shared channel nobody reads is the same as no detection at all.

    Operating rules worth writing down

    • Applies happen in CI, not on laptops, so every change has a reviewed plan and an audit trail.
    • Nobody edits state by hand except through terraform state commands, after a backup, with a second person present.
    • Console changes in production are incidents. If someone must make one, they open a ticket to bring Terraform back in line.
    • Pin provider and Terraform versions in each configuration, and upgrade one state at a time.

    Key takeaways

    • Split state so that one plan can only damage one bounded part of your estate.
    • The S3 backend now supports native locking with use_lockfile; DynamoDB-based locking is deprecated.
    • Enable bucket versioning and encryption on the state bucket, and restrict who can read state.
    • Share values between states through outputs or a parameter store, not by reaching into other states casually.
    • Run scheduled plans with -detailed-exitcode to detect drift, and route drift to the owning team.
